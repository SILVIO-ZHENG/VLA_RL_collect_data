## 用户已经确认的产品边界

- Nexus 是安装在机器人端或边缘设备上的模型部署与任务执行平台。
- Nexus 内绝对不做业务任务队列。排序、优先级、等待及业务重新调度全部由上层承担。
- 两种互斥操作模式：debug（界面启动）和 automatic（调度 API 启动）。另一个入口的启动请求必须被后端拒绝。
- 界面负责部署配置、调试、监控和经授权的人工干预。自动模式下界面不能直接创建/启动新的生产任务。
- 模型部署、就绪和任务执行是不同生命周期：点击部署不能使机器人运动；进入 automatic 也不能自动启动任务。
- 同一套业务源码兼容 5090 和 Thor，机器环境差异由配置表达。
- 视觉只上报事实；工作流决定暂停、复位和完成；实际动作仍受机器人端安全层约束。

## 必须实施的功能

### 1. 操作模式和接单控制

界面使用手动／自动名称（API 值仍为 `debug|automatic`），模式选择仅在运行设置页。模型部署、运行设置和实时监控是三个界面；根入口进入监控，优先显示活动任务，其次显示可用部署；多个部署时显式选择，没有部署则显示配置引导。进入或恢复自动需至少一个固定方案已校验、匹配已部署配置且模型健康；暂停状态不能通过切换模式解除。

引入独立于硬件运行方式的工作站模式 `debug|automatic`。现有 `nexus_deploy.site --mode simulate|observe|execute` 是硬件能力启动配置，不要用同一个字段替换或混淆它。

模式、接单开关和任务准入通过一个公共后端服务管理。初次安装默认 debug；服务重启后保留配置模式但默认关闭接单，展示需要恢复接单的原因。重启前未完成任务继续要求人工核实，不自动重启动作。

切换模式必须确认无活动任务、无正在执行/结果未知的停止或复位、机器人已确认空闲。未知状态不能算空闲。关闭接单只阻止新请求，不自动终止当前任务。

界面新建/开始、旧 `/api/deployments/.../start`、新接口和 `/api/sorting/tasks` 都必须走后端同一准入规则。不要只隐藏前端按钮。

### 2. 无队列的原子准入与部署就绪

每台机器人只允许一个已接受且未完全结束的任务。starting、running、paused、resetting、stopping、recovery_required 均占用执行名额。正在复位或调试的机器人也不能接受新业务请求。

调度请求只能选择已部署、已验证并已就绪的固定方案；不在调度请求中等待模型加载或别的批次释放资源。部署准备阶段仍可由界面显式加载模型；批次结束后的模型保留策略与任务结束分开，不要无条件杀掉共享模型。

先做同身份 request_id 幂等核对；同请求返回原任务，即使当前模式或接单状态已改变也不重新执行；参数冲突拒绝。对于真正的新请求，将模式、接单、就绪、占用检查与执行名额预留原子化。状态持久化失败不得开始动作，并在无法确认恢复时明确阻止继续执行。

忙、未就绪、模式冲突或接单关闭时返回明确 HTTP 状态和稳定 reason_code；忙/模式冲突建议 409，未就绪或接单关闭建议 503。被拒绝请求不得创建待执行条目，后来恢复空闲也不得自动执行。可记录拒绝审计。

HTTP 202 仅用于已占用执行名额并开始本次执行的任务，不表示业务排队。区分部署作业的内部准备阶段与业务排队语义，不为满足命名而无意义破坏旧模型管理流程。

### 3. Nexus 界面

沿用现有页面和风格，显示模式、接单状态、部署就绪情况、当前任务来源和拒绝原因。

- debug：可部署配置和人工调试启动；调度启动拒绝。
- automatic：显示等待调度或当前调度批次；禁止人工新任务启动；保留按权限的监控、暂停和结束。
- 自动批次在界面可发现并打开，不需要调度系统人工转发 task_id。
- 后端提供统一 TaskView，包括 task_id、来源、状态、revision、allowed_actions 和不可用原因。
- 命令执行时重新校验当前状态；人工暂停不能由视觉或重复调度调用自动恢复。
- 人工结束只有确认机器人停止后才视为 cancelled；复位失败或结果未知不能显示 completed。
- 分别呈现任务结果、服务健康和通知交付状态。无任务排队列表、优先级或“下一任务”按钮。
- 浏览器关闭不影响任务；健康检查不能依赖浏览器 GET 轮询。

保留现有操作员认证/CSRF 边界，调度 token 和内部视觉 token 不放入前端。

### 4. 视觉适配层与完整开发链路

从 ControlPlane 中隔离视觉启动/停止、健康与观察接收，定义轻量 PresenceProvider 契约；先保留真实 Sidecar 后端，增加 Mock 和录像回放输入，使业务工作流可以在没有 Thor 和机器人时验证。

录像回放使用相同的视觉模型/规则；机器人动作结果使用模拟适配器。支持对采样间隔、断流、旧代次和未知状态做测试。帧采集、推理和真实机器人执行不能因为测试而启动。

同一次控制模式下，视觉只发送标准观察；只有控制层拥有任务策略。梳理 `presence_control.py` 与 `presence_gate.py` 的重复职责，确保一份权威策略；删除或更改兼容接口前先检查导入和测试，不直接移除尚被使用的入口。

优先补齐独立于网页刷新的断流失效逻辑：长时间无有效观察、流重启、任务/generation 切换时，清空连续空场证据和需要重置的帧窗口。恢复后第一帧不能把断流时间计入“连续为空”。不能只修改 UI 提示文字。沿用现有 UNKNOWN 行为，不在本阶段未经验证添加新的真机自动暂停策略。

视觉最终完成条件仍是已确认的工作区空场、软暂停成功及复位成功。保留 `conveyor_delivery_independently_verified=false`。真实传送带送达没有独立信号；模拟结果不得伪装成物理 completed。现场 ROI、相机视角和视觉漏检验收仍需另行开展。

### 5. 任务与机器人执行接口

抽出足够窄的公共任务用例和机器人命令适配器，使 UI 和 SortingController 不再各自拼装启动规则。优先复用已有暂停/恢复/复位实现，避免改动伺服下发算法。

命令与任务代次关联，明确“已接受”和“已执行成功”的区别。测试适配器可以返回执行结果；真实执行结果超时归为待核实，不无限重发复位。暂停和复位保持现有安全检查。

## 验收要求

必须验证以下有意义的行为，而不只是检查函数是否存在：

1. debug 模式调度启动被拒绝；automatic 模式界面及旧 start 接口启动被拒绝。
2. 同时两个新请求只接受一个；被拒绝的请求在第一批结束后不会自动执行。
3. 相同 request_id 重试不启动第二次；冲突参数拒绝。
4. running/paused/resetting/recovery_required 时均不可插入新任务；模式切换与启动竞争不能绕过约束。
5. 未就绪拒绝，部署就绪后可执行；点击部署或切到 automatic 不触发动作；关闭接单不自行终止当前任务。
6. 调度启动后页面显示同一任务；人工暂停/结束结果与调度查询一致；关闭浏览器不影响状态更新。
7. 视频/Mock → 视觉观察 → 空场计时 → 模拟暂停回执 → 模拟复位回执 → simulated → 查询和可选回调闭环。
8. 断流、UNKNOWN、旧代次、重复序号、复位失败/超时、人工结束均不能误报物理完成。
9. 回调先失败再成功，不重启机器人任务，event_id 与原事件载荷保持稳定。
10. 前端用实际可用的浏览器或现有工具验证模式、按钮和错误反馈；两种机器配置均可解析，避免新增 5090 专属路径到业务源码。
