# G2A 机器人客户端使用说明

## 快速启动

正式部署包的根目录是 `/home/agi/deploy/g2a_robot_client`。推荐由 Nexus
任务页启动 Client；手工启动 PI0.5 只读观测时使用：

```bash
ssh g2
cd /home/agi/deploy/g2a_robot_client

# 有输出表示可能已有会话，不要重复启动
pgrep -af 'python3? -m [r]obot_client'

./robot_client/run.sh \
  --host=10.42.1.200 \
  --port=5557 \
  --task="Pick a package from the box with the left gripper and place it on the table. Then pick it up with the right gripper and place it on the conveyor belt, keeping the QR code facing upward." \
  --inference-mode=async \
  --read-only \
  --duration-s=60
```

PI0.5 使用 `5557`，LingBot-VLA-v2 使用 `5558`。有线策略 Server 地址是
`10.42.1.200`；无线回退时把 `--host` 改为 `192.168.110.140`。`--dry-run`
不访问 GDK，`--read-only` 读取 joints/图像并推理但不下发动作。按
`Ctrl+C` 正常结束手工 Client。未完成已标定安全 profile、急停和低速验收时
不得使用 `--execute`。

该目录可以脱离 LeRobot 项目整体复制到机器人。机器人端不加载模型，不依赖
PyTorch、Transformers、Draccus、LeRobot 或 msgpack。

客户端使用通用 `nexus-policy-websocket` v2 协议，可连接 PI0.5 或 LingBot-VLA-v2。
迁移期间仍接受 `g2a-policy-websocket` v2 与历史 `g2a-pi05-websocket` v1。
具体支持的推理模式以服务端 metadata 为准；LingBot 当前支持 sync/async/RTC，RTC 在完成
真实相机 read-only 验收前禁止 execute。

运行时依赖：

- 机器人原生 `agibot_gdk`
- 机器人原生 NumPy
- `websockets>=13,<17`；G2当前已有13.0.1，也可通过`wheels/`离线携带

图像不在机器人端使用 OpenCV 解码。GDK 的 JPEG 或 raw bytes 会连同尺寸和颜色
格式发送到 GPU server，由 server 统一校验并转换为 HWC uint8 RGB。

`run.sh`和`debug_python.sh`会把GDK底层glog日志统一保存到部署包的
`logs/gdk/`，不再把`python3.10.log.INFO.*`文件写到部署包根目录。需要改到
其他位置时，可以在启动前设置`GDK_LOG_DIR`。

```bash
  --read-only \

```

### 只读采集模型原始action

下面的诊断会固定第一次采集的state和三路图像，连续请求模型20秒。这样可以在
输入字节完全一致的条件下检查模型采样和相邻chunk是否稳定。程序只初始化GDK
读取接口，绝不会调用控制接口：

```bash
./robot_client/run.sh \
  --host=<GPU_SERVER_IP> \
  --port=5557 \
  --task="<训练数据中完全一致的task文本>" \
  --inference-mode=async \
  --read-only \
  --duration-s=20 \
  --execution-fps=30 \
  --servo-fps=100 \
  --prediction-horizon=50 \
  --quality-horizon=50 \
  --min-replan-after-steps=1 \
  --request-lead-margin-steps=8 \
  --action-trace-dir=./logs/action_traces \
  --freeze-trace-observation \
  --log-file=./logs/model_action_trace_read_only.log
```

每次请求都会立即写入
`logs/action_traces/<时间戳_session>/requests/request_*/`：

- `trace.npz`：请求时24D state和server返回的原始30Hz absolute action chunk；
- `metadata.json`：prompt、chunk ID、RTT、推理耗时、RTC信息和采集时间；
- `images/`：实际发送给server的三路图像；
- 根目录`servo_samples.npz`：客户端生成的100Hz插值轨迹，仅记录、不发送。

移除`--freeze-trace-observation`即可采集实时变化的observation。建议先做固定OBS
实验，再做实时OBS实验；两者使用不同的自动时间戳目录，不会覆盖。

把结果复制到GPU服务器后生成报告：

```bash
conda run --no-capture-output -n lerobot \
  python src/nexus_deploy/vla/pi05/analyze_action_trace.py \
  /path/to/<时间戳_session>
```

输出位于trace目录下的`analysis/`，包括`summary.md`、`joint_metrics.csv`、
每次请求的24D图、每个关节的位置/一阶差分/二阶差分图，以及100Hz插值图。

为了只读评估最终100Hz低通和固定夹爪，可以追加：

```text
--action-low-pass-cutoff-hz=4 --hold-effectors
```

低通是NumPy实现的一阶因果滤波，位于最终GDK调用之前；默认关闭。`--hold-effectors`
会把双夹爪固定在客户端启动时实测位置，默认也关闭。使用`--read-only`时两者只改变
trace中的虚拟100Hz action，不会调用GDK控制接口。

确认关节顺序、三路图像、prompt、网络延迟和 action 输出后，才允许短时间执行：

```bash
./robot_client/run.sh \
  --host=<GPU_SERVER_IP> \
  --port=5557 \
  --task="<训练数据中完全一致的task文本>" \
  --inference-mode=async \
  --execute \
  --duration-s=10 \
  --execution-fps=30 \
  --servo-fps=100 \
  --prediction-horizon=50 \
  --quality-horizon=50 \
  --min-replan-after-steps=1 \
  --request-lead-margin-steps=8 \
  --min-rtc-blend-steps=8 \
  --watchdog-timeout-s=3 \
  --relative-target-mode=warn
```

server 返回的三种模型输出全部是 canonical 24D absolute action。机器人 client
不会再次把 delta 累加到 state。默认只对双夹爪物理绝对范围进行裁剪；身体和
夹爪的相对变化阈值只打印 warning，不裁剪。

client会根据server metadata自动选择GDK当前位置初始化范围。`16d_delta`和
`16d_absolute`在策略client启动时只重新接管双臂，不调用`move_head_joint`，
也不重新规划腰部；因此应先运行下面的reset脚本，把头部和腰部恢复到训练数据
初始姿态，策略执行期间再保持该实测姿态。`24d`会初始化双臂、腰部和头部，
头部初始化失败时最多重试3次。
所有execute模式在当前位置初始化后等待1秒再启动100Hz servo。启动或运行中的
未捕获异常会同时打印到终端并完整写入`--log-file`。

`--execute`启动后先做5次warm-model延迟预检。在rolling P95连续性预算和首个可执行
chunk都通过前，action线程不会调用GDK；预算不足会打印`Refusing --execute`并退出。

当前真机执行使用 `--inference-mode=async`。RTC 只允许先在 `--read-only` 下完成专项验收；
RTC 的可变 prefix、stale 丢弃和最小融合逻辑见部署目录中的 `ASYNC_RTC.md`。

`--execution-fps=30`（兼容别名`--fps`）是Client消费action、计算RTC stale steps和
buffer时间的频率，不再要求与Server的训练频率一致。不同频率会打印轨迹时间缩放
warning。30 FPS训练轨迹按15 FPS执行时，50步约3.33秒、30步RTC horizon约2秒。
`--servo-fps=100`是机器人GDK下发频率，两者不能混用。client会按单调时钟对
action chunk做无超调的线性插值，以固定100Hz调用
`joint_servo_control(control_period=0.01, enable_low_latency=True)`。新chunk
从最后一次成功发送（包括裁剪后）的action开始平滑过渡；等待推理期间继续以
100Hz保持最后目标。

三路相机使用 GDK 原始 `timestamp_ns` 对齐，不再用逐路读取完成后的主机时间冒充
帧时间。每次观测先取头相机作为时间锚点，再通过 `get_nearest_image` 选择左右腕
相机帧；默认容差为 5 ms。考虑到三路 DDS 发布可能有短暂先后，客户端以 2 ms
间隔等待最多 40 ms；仍无法对齐时该次观测失败，不会把跨帧图像发送给模型。
三路帧全部选定后才进行腕部 JPEG 解码和 640×400 缩放，因此图像处理耗时不会
污染相机帧时间戳。相关参数为 `--camera-sync-tolerance-ms`、
`--camera-sync-timeout-ms` 和 `--camera-sync-poll-ms`。

`--execute` 的 GDK 控制模式也采用两阶段启用：连接、协议校验、模型预热、相机读取
和延迟预检均只读取硬件；全部通过后才显式执行当前位置初始化。初始化完成前，
adapter 会拒绝任何 `send_action`。

## 大寰夹爪循环并复位到固定身体姿态

正式入口使用部署包内版本化姿态
`BODY_RESET_PROFILE_ID=g2_sorting_home_20260817_v1`。目标定义在
`robot_client/constants.py::BODY_RESET_TARGET_24D`，其中身体22关节与现场确认的
G2复位姿态逐值一致。正式入口固定使用大寰 profile，先执行两只夹爪
`0.025 m 松开 → 等待0.5秒 → 0 m夹紧 → 等待0.5秒 → 0.025 m最终松开`，
再移动22个身体关节。`--scope`只记录模型配置，不决定是否跳过头腰。

通过正式入口复位22个身体关节时，在部署包根目录运行：

```bash
./robot_client/reset_all_joints.sh
```

该命令会直接执行物理复位，不进入预览模式，也不要求输入确认词。运行前必须
清空机器人工作区、停止其他GDK client并确认急停可用。

首先只预览当前位置、最终目标和每个关节的差值：

```bash
./robot_client/debug_python.sh ./robot_client/reset_to_dataset_start.py \
  --scope=24d \
  --effector-profile=dahuan \
  --cycle-effectors
```

确认工作空间无障碍物、急停可触达且其他client全部停止后，才执行：

```bash
./robot_client/debug_python.sh ./robot_client/reset_to_dataset_start.py \
  --scope=24d \
  --effector-profile=dahuan \
  --cycle-effectors \
  --effector-cycle-pause-s=0.5 \
  --execute
```

`--execute`启动后会直接执行，不再要求输入交互式确认词。平台入口因此额外要求二次确认。
脚本使用GDK带速度的关节规划接口，默认身体速度为`0.15 rad/s`，监控实时反馈，并在
超时、异常或Ctrl+C时请求保持当前姿态。夹爪每段均读取反馈并验证到位；下发采用
`0.0025 m`最大插值步长、`0.02 s`控制周期和每步3次发送，避免端点跳变。头部目标
发送遇到瞬时GDK失败时最多重试3次。夹爪每个阶段有独立的8秒到位超时；任一阶段
失败会停止后续序列并请求保持当前姿态，不会继续身体复位。

复位脚本、只读测试和部署client共享
`/tmp/g2a_pi05_robot_gdk.lock`进程锁，不能同时访问GDK。每次预览或执行的报告
保存在`logs/reset_to_dataset_start/`。报告记录复位profile、初始/目标/最终身体姿态和
错误状态、夹爪profile、三段序列及两段停顿时间。

## 并发模型

- ActionPlan始终按30Hz policy step维护chunk、RTC和stale-step计数。
- action线程按`--servo-fps`（默认100Hz）基于时间线性采样30Hz轨迹，并独占
  GDK Robot控制调用；100Hz tick不会被误计为policy step。
- inference线程仅在需要重新推理时采集三路图像。
- GDK Camera 调用不持有 action 控制锁。
- state 读取与 action 写入使用同一 Robot 锁，避免同时访问 GDK Robot 对象。
- 网络断开后清空待执行 chunk；已有成功 action 按既定策略继续保持。

日志每秒汇总一次实际servo周期、SDK发送耗时和deadline miss，例如：

```text
Servo timing target=100.0Hz ... loop_ms(mean/p95/max)=... send_ms(mean/p95/max)=... deadline_misses=0
```

## 夹爪工作面硬安全层（需要配置并核验后显式启用）

`safety_layer.py`在最终100Hz target通过低通、速度/加速度和GDK绝对关节限位后，
使用本次下发前重新读取的真实关节反馈计算FK。同步线程使用逐 collision frame 的保守
包围球检查当前/中点/目标；危险目标会被拒绝。execute模式先用最新反馈复检上一条GDK
成功动作，通过则主动保持上一条动作，否则保持真实反馈。AgiBot官方G2 Omnipicker
URDF、G2 大寰左右末端六个网格的 25,033 个去重顶点和夹爪 mimic 关系的详细路径搜索/二分位于单槽后台线程。
后台候选只有目标仍匹配且用最新反馈再次通过同步守门后才可能采用，不能直接下发。

同步守门默认预算8ms；超时当拍保持真实反馈，连续3次超时停止命令流。碰撞拒绝会输出
限频WARNING，包含保持方式、原因、surface和point；每拍安全JSONL仍由有界后台队列写入。
队列满或写线程失败会停止后续执行，不会在100Hz线程同步序列化/打开文件。
当前 G2 大寰工作面采用 3 mm 接近预警和 1 mm 硬拦截；预警不修改动作。只读模式在
保守包围球命中后会用详细网格复核，平台和 JSONL 发布详细网格的真实桌面距离。

随包提供的`SAFETY_CONFIG_TEMPLATE.json`固定为`calibrated=false`，不能直接用于
真机。复制模板后配置`surfaces[]`中的桌面/传送带高度、可选XY范围，并核对
`base_link`坐标和实机FK，才可改为`true`并先做read-only验证。官方资产来源、commit、
许可证和SHA见`assets/agibot_g2/SOURCE.json`：

```bash
./robot_client/run.sh ... --read-only \
  --safety-config=./robot_client/g2a_table_safety.calibrated.json \
  --safety-log-file=./logs/g2a_table_safety.jsonl
```

配置、FK或GDK反馈异常会停止控制，不会绕过安全层继续下发。第一轮只启用hard
constraint；soft scaling和dynamic chunk尚未启用。
